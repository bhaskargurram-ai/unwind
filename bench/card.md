# ReversiBench — Dataset Card

ReversiBench is the labelled corpus + live sandbox behind Unwind (PROJECT.md
Deliverable 2, §5, §8). It answers the empirical question no prior work asks:
**which of the real MCP ecosystem's tools are reversible, and how?** This card
documents sources, licences, strata, the split policy, IAA plan, and limitations
— its integrity is critical to the paper's claims.

> **Status:** the artefacts committed here (`seed_labels.jsonl`, the mock servers,
> the scenario traces) are a **small, clearly-marked illustrative seed** that
> makes the pipeline runnable and testable. They are **not** the full corpus and
> carry **no headline results**. Full-scale labelling follows the protocol below.

---

## 1. Composition

| Component | What it is | Where |
|---|---|---|
| Tool catalog | Raw `ToolSpec` rows crawled from public MCP servers (name/description/schema only). | crawler: `catalog/crawler.py`; data (gitignored): `catalog/data/` |
| Labels | Per-`(tool, environment)` reversibility annotations (R-class + blast radius + externality + half-life). | schema: `labeling/schema.py`; seed: `labeling/seed_labels.jsonl` |
| Sandbox | Real (filesystem/git/sqlite) + mock (comms/payments) servers where forward+inverse actually execute. | `sandbox/` |
| Scenarios | Destructive end-to-end traces for agent-level eval. | `scenarios/*.json` |

**Unit of labelling:** a `(server, tool, environment)` triple. Because
reversibility is environment-relative (§5.2), the *same* tool under two
environments is two distinct units (e.g. `write_file` is R1 versioned, R4
versionless).

---

## 2. Sources & licences

Servers to sample are declared in `catalog/sources.yaml`, **stratified by domain**
(PROJECT.md §8): `files, vcs, db, comms, payments, crm, cloud, calendar`. The
corpus targets the ecosystem scale the PolicyLayer audit establishes (~2,031
servers / 31,000 tools) as its sampling frame.

- Reference servers (filesystem, git, sqlite) are MIT-licensed; the in-repo mock
  comms/payments servers are Apache-2.0 (this repo's licence).
- Each `sources.yaml` entry records the upstream licence. Servers requiring
  credentials list env-var **names** only; **values are never committed**.
- **Crawled data is never committed** (PROJECT.md §12): only the crawler and a
  content-hash manifest (`catalog/hashes.json`, produced by
  `crawler.hash_catalog`). A reviewer re-crawls and checks the hash.

---

## 3. Split policy — SERVER-DISJOINT (non-negotiable)

Train / calibration / test splits are **by server, never by tool within a
server** (PROJECT.md §8; `CLAUDE.md` benchmark hygiene). Rationale: sibling tools
on one server share lexical and schema patterns (`create_page`/`delete_page`/
`update_page`), so a tool-disjoint split leaks those patterns across train and
test and **inflates results**. Splitting by server removes the leak.

- **Calibration thresholds (escalation policy, confidence calibration) are fit
  ONLY on the calibration split, never on test.** Test is touched once, for the
  final numbers.
- Splits are stratified so each domain appears in every split where possible.
- Split assignments are recorded per server in the (gitignored) crawl manifest and
  pinned by server commit hash for reproducibility.

---

## 4. Labelling & IAA plan

- **≥2 independent annotators** per sampled unit, following `labeling/guide.md`
  (published, per §8). Annotators do not confer before submitting.
- **Agreement** is reported with **ordinal Krippendorff's α** and **Fleiss' κ**
  (`labeling/iaa.py`) — ordinal so an R4-vs-R3 disagreement counts as milder than
  R4-vs-R0, matching the R-scale's asymmetric loss (§5.1).
- **Disagreements are adjudicated** by a third annotator and recorded as
  `AdjudicatedLabel(was_disagreement=True)`; the **disagreement rate is reported**.
- Annotator golden rule: when genuinely unsure, assign the **more irreversible**
  class (fail safe).

---

## 5. Live validation (fidelity is measured, not asserted)

Rollback fidelity (§8.B) is **only credited from the live sandbox**
(`sandbox/harness.py`): the harness runs `pre_read → forward → inverse` and diffs
state, grading `exact / semantic / acceptable-approximation / failed` and
recording **residue**. A model's claim that "the inverse works" is never accepted
as evidence. The mock comms/payments servers exist precisely so R3/R4 tools
(sends, settled charges) can be validated safely; real servers cover R0–R2.

---

## 6. Metrics

All five §8 metric families are computed by `eval/` and regenerated by
`make results` (writes to the gitignored `paper/`). Every headline number carries
a bootstrap 95% CI (`eval/stats.py`); system comparisons use paired tests.

---

## 7. Known limitations

- **Descriptions are the only briefing** and 96.1% carry no consequence warning
  (§1) — some units are genuinely under-determined from schema alone. This is a
  *finding*, not just a limitation (validates Mind-the-GAP; see §15 risk pivot).
- **Environment coverage is finite:** we enumerate a fixed set of
  `EnvironmentDescriptor`s; real deployments vary continuously.
- **Mock ≠ production** for comms/payments: mocks reproduce the *reversibility
  structure* (windows, externality, residue) but not provider-specific quirks.
- **The committed seed is illustrative** (~30 labels), not the corpus; no result
  should be quoted from it.
- **Half-life ground truth** is provider-documented where available and estimated
  otherwise; `eval.compensation.half_life_accuracy` reports MAE + tolerance rate
  so estimation error is visible.

---

## 8. Ethical / safety notes

The sandbox never touches real recipients, real money, or real infrastructure —
comms/payments are mocked and filesystem/git/sqlite run on disposable sandbox
state (gitignored). Destructive scenarios are simulations for measuring a *guard*,
never executed against production systems.
